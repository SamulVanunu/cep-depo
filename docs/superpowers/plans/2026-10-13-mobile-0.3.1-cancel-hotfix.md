# Mobile 0.3.1 Cancel Hotfix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Android `0.3.1` (`versionCode` 4) so cancelling an APK download gives immediate feedback, blocks overlapping retries until native cleanup settles, and leaves no partial file or download metric.

**Architecture:** Extend the existing download hook state machine with an explicit `cancelling` phase rather than pretending native cleanup has already finished. Keep ownership of the active operation until `download()` rejects with `ApkDownloadCancelledError`; the panel renders immediate cancellation feedback during that interval and returns to idle only after cleanup. Version and verify the existing EAS internal APK release without adding notification, TV, support, migration, or OTA work.

**Tech Stack:** Expo SDK 57, React Native 0.86, TypeScript, Jest with React Native Testing Library, EAS Build, Android APK tooling

**Spec:** `docs/superpowers/specs/2026-10-13-mobile-tv-notifications-support-design.md`

## Global Constraints

- `0.3.1` contains only cancellation hardening; all `0.4.0` TV, support, push, database, admin, and Edge Function work remains out of scope.
- Set Expo version to exactly `0.3.1` and Android `versionCode` to exactly `4`.
- Native cancellation is requested once; active operation ownership remains until its promise settles and partial-file cleanup completes.
- Cancellation never writes download history or metrics and is not displayed as an error.
- Do not add OTA configuration or publish an EAS update.
- Do not start EAS Build, publish an APK, or modify hosted services without a separate explicit approval at the named gate.
- Do not commit `.memory/CURRENT.md` without explicit approval.

## Review Focus

- Native cancellation remains pending after the press: UI must immediately show `İndirme iptal edildi. Kısmi dosya temizleniyor.` and must not start a second operation.
- Cancellation occurs while destination preparation is pending: no native task starts after preparation resolves, and the partial destination is cleaned.
- User presses cancel repeatedly: the native task receives exactly one cancellation request.
- Detail screen unmounts while cancellation settles: no post-unmount state update, metric, history write, or installer launch occurs.
- Release configuration drifts between display version and Android code: the config test must pin `0.3.1` and `4` before build.

- [ ] **Step 4: Implement the minimal hook transition**

In `src/features/downloads/useApkDownload.ts`:

- Add `cancelling` to `DownloadPhase`.
- Add `cancelRequestedRef = useRef(false)`.
- Reset `cancelRequestedRef.current = false` only when a new operation is accepted in `start`.
- In `cancel`, return unless an operation exists or if cancellation was already requested; otherwise set the ref, call `operation.cancel()` once, clear the visible error, and set `phase` to `cancelling`.

- In the cancellation catch branch, clear operation/busy ownership, reset the cancellation ref, and set `idle` only when mounted.
- Ensure success/error branches reset cancellation state without changing existing installer behavior.
